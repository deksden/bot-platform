# A07 Review: error handling, reliability, and concurrency

## Что уже хорошо

- В shared framework-слое уже есть правильные базовые guardrails, на которые можно опереться без изобретения новой reliability-модели: нормализованные boundary errors (`NotFound` / `Conflict` / `Validation` / `Unavailable`), явные idempotency expectations и требование описывать atomicity/eventual-consistency живут в `/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/persistence-interface-and-store-boundary.md:69-103`. Это сильный фундамент для `Membership`, `Channel`, `PipelineBinding`, `ImportRun` и activation flows.
- Workflow substrate уже требует то, чего обычно не хватает в подобных wave-документах: `WorkflowStartRequest` с correlation/idempotency key, стабильный run id, idempotent callbacks, явные lifecycle states, retry/resume visibility и protected internal auth (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/workflow-framework-contract.md:62-152`). Значит, для bot submission -> backend workflow есть готовый канон, его нужно просто не потерять в `PRT-040`.
- Для control-plane mutation уже зафиксированы правильные safety rules: один backend-owned validation path для channel binding и audit trail на каждую configuration mutation (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md:150-192`). Это хороший барьер против race-prone UI/CLI logic drift.
- Access model тоже поставлен в правильную позицию: server-authoritative checks, machine-readable allow/deny reasons, persisted session truth и явное разделение operator auth vs channel/customer identities (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/security/auth-and-access.md:49-98`, `/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/security/auth-and-access.md:128-130`).
- В `PRT-040` уже есть важная “honesty first” линия: processor обязан классифицировать элементы как `supported` / `degraded` / `unsupported`, а bot-mediated import не должен становиться silent review bypass или direct activation path (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:88-109`, `/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:122-132`).
- Product overlays уже показывают более строгую reliability-модель, чем общие child protocols пока формулируют. В Docoved активный snapshot оформлен как явный state machine с source-scoped activation lock и idempotent activation retry (`/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/runtime/docoved-memory-bank-publication-and-active-snapshot-model.md:121-159`), а source binding обязан fail closed без угадываний и без silent fallback на другой source (`/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/runtime/docoved-access-and-knowledge-source-binding-model.md:31-89`).
- Seller overlay правильно предупреждает о reliability-ловушке смешанных surfaces: legacy `upload/activate` признан transitional, потому что смешивает snapshot upload, transport apply и live activation и создает split-brain относительно publish/release model (`/Users/deksden/Documents/_Projects/seller-agent/.memory-bank/guides/explanation/business-profile-publication-model.md:129-141`). Это хороший антипример для `PRT-040`.

## Пробелы и риски

- `PRT-039` фиксирует shared objects, capabilities и surface classes, но почти не задает mutation semantics для concurrency/conflict cases (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:70-105`, `/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:158-224`). Сейчас не сказано, какие операции на `Membership`, `Channel` и `PipelineBinding` являются compare-and-swap, какие last-write-wins запрещены, где должен быть `Conflict`, а где `Validation`. Риск: lost update при параллельном role change/revoke, двойное изменение pipeline binding, stale overwrite transport config.
- В control-plane слое нет явной защиты от stale binding для in-flight executions. `Channel` уже несет `product_instance_ref`, `entry_pipeline` и `binding_status`, а `ExecutionRun` объявлен shared object (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:72-82`, `/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:124-134`), но протокол не требует, чтобы при принятии execution/import run фиксировался effective config snapshot. Без этого channel rebinding, policy override change или source reassignment посреди workflow делают run нерепродуцируемым и затрудняют safe retry.
- `PRT-040` описывает ImportRun слишком крупными мазками: `receive -> create ImportRun -> process -> candidate revision -> report -> approve/activate` (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:111-120`). Не хватает явного lifecycle vocabulary уровня `accepted/queued/running/waiting/retrying/completed/failed/canceled/superseded`, attempt accounting и связи с workflow callback model из framework contract (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/workflow-framework-contract.md:62-97`, `/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/workflow-framework-contract.md:121-152`). Риск: double-submit, ambiguous “failed”, orphaned status после host restart, невозможность различить retry того же run от нового run.
- Для bot submission boundary нет явной dedup/idempotency policy. `PRT-040` говорит, что bot может submit input и track status (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:122-127`), но не фиксирует, что считается “той же семантической операцией”: повтор того же message/file set, повтор после timeout на user-facing reply, повтор workflow callback, повтор review command. На фоне общего framework requirement “repeated submissions should converge” (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/persistence-interface-and-store-boundary.md:82-91`) это заметная дыра.
- Shared layer пока недостаточно явно отделяет import completion от activation concurrency. `PRT-040` справедливо оставляет activation policy product-local (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:134-147`), но из-за этого легко недоописать минимальный shared invariant: singleton active revision per scope, activation only from verified/review-approved state, compare-and-swap cutover, idempotent retry и visible lock contention. Product overlay Docoved это уже формализует (`/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/runtime/docoved-memory-bank-publication-and-active-snapshot-model.md:121-159`), а shared protocol пока нет.
- Membership/access changes описаны как capability vocabulary и server-authoritative checks, но не как time-sensitive mutation boundary (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:88-116`, `/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/security/auth-and-access.md:49-98`). Неясно, когда re-check authority обязателен: только на session resolve, на каждый mutating command, на review decision, на activation, на long-running CLI flow? Риск: stale privileged session или давно открытая admin surface успевает одобрить import / поменять binding после role revoke.
- Взаимодействие “bot submits, backend workflow runs, operator reviews” пока не имеет общей failure policy на стыках transport delivery и durable acceptance. Workflow contract требует stable run id уже на acceptance (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/workflow-framework-contract.md:73-77`), но `PRT-040` не говорит, что bot/UI не должны отвечать “import started”, пока durable `ImportRun` не создан. Риск: backend принял run, а user-facing acknowledgment потерялся; пользователь жмет submit еще раз; система создает второй import.
- В child protocols почти не проговорено, какие failures должны быть operator-visible, loggable и incident-worthy, а какие можно показать как friendly validation state. Между тем observability contract требует no-silent-fallback, retry only for idempotent operations, terminal traceable state и explicit incident capture на unexpected/invariant errors (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/observability-and-incident-diagnostics.md:220-268`). Сейчас для channel conflict, activation lock contention, unauthorized source override, missing active snapshot, duplicate import collision и workflow unavailability явной severity/escalation policy в `PRT-039/040` нет.
- `PRT-039` правильно ограничивает direct-admin chat narrow toggles (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:178-188`), но не уточняет, какие toggles вообще безопасны при concurrency. Без этого “узкий toggle” легко превращается в race-prone shortcut для rebinding, pause/resume activation или access override без precondition checks.

## Что убрать/не вводить

- Не вводить blind last-write-wins для `Membership`, `Channel`, `PipelineBinding` и review/activation commands. Для этих объектов надежность важнее “простого upsert”.
- Не вводить friendly auto-retry/auto-resubmit на bot import boundary без explicit idempotency key и semantic dedup rule. Иначе самый user-friendly UX породит duplicate import runs.
- Не вводить silent fallback на “другой knowledge source”, “предыдущий binding”, “старую active revision” или “direct in-process import вместо workflow host”. Для этого уже есть прямой запрет на silent fallback и explicit-failure model (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/observability-and-incident-diagnostics.md:220-228`, `/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/runtime/docoved-access-and-knowledge-source-binding-model.md:72-89`).
- Не вводить shared generic `upload/activate` shortcut, который смешивает processing, review и live cutover. Seller overlay уже показывает, что это unreliable split-brain pattern (`/Users/deksden/Documents/_Projects/seller-agent/.memory-bank/guides/explanation/business-profile-publication-model.md:129-141`).
- Не вводить second public workflow API или callback-by-secretless-URL ради удобства import/chat flows. Workflow contract уже явно помечает это как anti-pattern (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/workflow-framework-contract.md:107-119`).
- Не вводить преждевременно глобальный distributed lock service или cross-product activation coordinator. Здесь нужен сначала узкий per-scope concurrency contract, а не новая инфраструктурная платформа.

## Что минимально добавить в протокол

- Для `PRT-039` нужен короткий, но обязательный mutation error policy для `Membership`, `Channel`, `PipelineBinding`:
  - normalized outcomes `Validation` / `Conflict` / `NotFound` / `Unavailable`;
  - machine-readable deny reasons для access failures;
  - запрет hidden retries на ownership/version conflicts.
- Для shared mutable objects нужен explicit precondition/version rule:
  - `if_version` / `expected_revision` / equivalent compare-and-swap contract для membership changes, channel binding updates, policy/source binding updates и review decisions;
  - если precondition не совпал, операция завершается `Conflict`, а не молча перетирает состояние.
- Для `PRT-040` нужен явный `ImportRun` lifecycle и attempt model, согласованный с workflow framework:
  - минимум `accepted`, `queued`, `running`, `waiting_review`, `retrying`, `completed`, `failed`, `canceled`, `superseded`;
  - stable `import_run_id`;
  - correlation/idempotency key на start boundary;
  - правило, что retry того же semantic import либо converges to existing run/effect, либо оформляется как новый явный attempt.
- Нужно зафиксировать effective-binding snapshot at acceptance:
  - resolved `channel_ref`;
  - `product_instance_ref`;
  - `pipeline_id` + validated args hash;
  - effective policy ref;
  - effective `knowledge_source_ref` / candidate revision ref when relevant.
  Это минимально нужно для reproducible diagnostics и safe retries после concurrent admin changes.
- Нужно добавить shared activation invariant, даже если detailed policy остается product-local:
  - только один active revision per declared scope;
  - activation only from verified/review-approved state;
  - cutover is atomic compare-and-swap;
  - retry того же verified activation idempotent;
  - lock contention/operator conflict видны как first-class states/events, а не растворяются в generic failure.
- Нужна явная rule for access-sensitive decisions:
  - review/activation/membership/channel mutation commands всегда re-check server-side authority at decision time;
  - long-running workflow acceptance не должна автоматически давать право на поздние mutating decisions;
  - membership revoke blocks subsequent sensitive commands even if UI/CLI page was opened earlier.
- В `PRT-039/040` нужна короткая escalation matrix:
  - `warn`: degraded processing, duplicate delivery safely deduped, lock contention with successful retry;
  - `error`: contract violation, stale-version conflict after user action, missing active snapshot, unauthorized source override, workflow host unavailable;
  - incident-worthy: impossible state, repeated activation lock starvation, duplicate active revision, no-silent-fallback breach.

## Premature abstractions

- `ActivationDecision` как отдельный shared object в `PRT-040` пока premature (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:69-71`). Сначала нужно зафиксировать минимальные activation invariants и conflict semantics; только потом решать, нужен ли отдельный cross-product entity type.
- Reusable protected-shell, forms и diagnostics primitives не стоит расширять в “shared write orchestration framework”, пока не описаны version/precondition semantics для membership/channel mutations (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:158-217`). Иначе UI abstraction приедет раньше safety contract.
- Отдельный source-processing service по-прежнему premature; здесь протокол держит правильную линию “package seam first” (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:149-157`). Для reliability сейчас важнее корректный run/attempt/activation contract, чем новая distributed topology.
- Не стоит добавлять сверх-общую “universal concurrency layer” или общий workflow/mutation orchestrator для всех control-plane и import cases. На этом этапе достаточно нескольких узких invariants: idempotent start, explicit conflict, compare-and-swap activation, effective config snapshot, decision-time access recheck.
