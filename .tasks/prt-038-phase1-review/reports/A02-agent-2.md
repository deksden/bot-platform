# Что уже хорошо

- Базовый shared vocabulary уже зафиксирован достаточно узко и в правильных слоях: identity/access (`User`, `Principal`, `Session`, `Membership`, `Workspace`), control-plane (`ProductInstance`, `Channel`, `PipelineBinding`) и governed-content/runtime artifacts (`ConnectedSource`, `SourceRevision`, `ImportRun`, `ProcessingArtifact`, `ExecutionRun`, `TraceArtifact`). Это хороший старт, потому что набор не пытается сразу моделировать весь продуктовый мир (`.memory-bank/spec/project/three-layer-product-line-architecture.md:127-142`, `.memory-bank/plans/protocols/PRT-038-platform-product-line-convergence-and-shared-substrate-extraction.md:141-156`).
- Отдельно хорошо, что auth vocabulary уже отделяет operator/admin identity от customer/channel identity и не дает смешать operator principal с runtime actor из транспорта. Это ровно тот semantic boundary, который потом защищает и `Membership`, и `Session`, и channel-bound execution (`.memory-bank/spec/security/auth-and-access.md:26-30`, `.memory-bank/spec/security/auth-and-access.md:41-60`).
- В SellerAgent и Docoved product-local meaning проговорен явно, а не оставлен “на потом”. Для SellerAgent зафиксировано, что business-profile publication и release assignment остаются продуктовой истиной; для Docoved зафиксировано, что `knowledge_source_ref`, active snapshot, grounding и activation semantics остаются локальными (`/Users/deksden/Documents/_Projects/seller-agent/.memory-bank/guides/explanation/business-profile-publication-model.md:29-43`, `/Users/deksden/Documents/_Projects/seller-agent/.memory-bank/guides/explanation/business-profile-publication-model.md:72-117`, `/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/runtime/docoved-access-and-knowledge-source-binding-model.md:31-48`, `/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/plans/protocols/PRT-038-docoved-shared-platform-adoption-control-plane-and-workflow-backed-knowledge-import.md:250-280`).
- `PRT-040` в целом держит правильную линию против false generic content: shared слой ограничен substrate для source/import processing, а interpretation, review и activation policy оставлены продуктам. Это особенно важно, потому что в Docoved shared contract уже нужен, а в SellerAgent reuse допускается только там, где semantics реально совпадают (`.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:60-75`, `.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:134-147`).

# Пробелы и риски

- Самая заметная semantic drift-зона сейчас между `ConnectedSource` и `KnowledgeSource`. Umbrella/shared vocabulary фиксирует `ConnectedSource`, но control-plane surface spec уже использует `KnowledgeSource` как canonical object class и как write surface (`.memory-bank/spec/project/three-layer-product-line-architecture.md:137-140`, `.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md:80-108`). Для Docoved это еще можно читать как product-local read model, но в platform-level spec это пока не проговорено явно. Риск: `KnowledgeSource` незаметно станет второй shared сущностью рядом с `ConnectedSource`, хотя по смыслу это либо product-local projection, либо UX label.
- Есть вторая несостыковка вокруг execution vocabulary: shared vocabulary и child protocol используют `ExecutionRun`, а runtime kernel canonical vocabulary описан как `ExecutionSession` (`.memory-bank/spec/project/three-layer-product-line-architecture.md:139-142`, `.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:72-82`, `.memory-bank/spec/runtime/agent-execution-kernel.md:84-97`). Без явного отношения “`ExecutionRun` = durable/read-model envelope over kernel `ExecutionSession`” остается двусмысленность между domain artifact, runtime lifecycle object и operational read model.
- В `PRT-040` уже проскочила лишняя потенциальная shared сущность: список shared governed-content objects включает `ImportReport`, хотя canonical shared vocabulary в umbrella/spec его не содержит, а дальше по тексту report описывается скорее как обязательный outcome/shape у `ImportRun`, а не как отдельный object root (`.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:62-68`, `.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:159-167`). Это прямой сигнал, что vocabulary еще не до конца стабилизирован.
- Ownership правила для product-local bindings пока частично понятны из product docs, но недостаточно сформулированы в shared protocol. Docoved очень четко говорит, что channel-bound surface не дает caller'у произвольно override-ить `knowledge_source_ref`, и что `knowledge_source_ref` остается product meaning поверх shared `ConnectedSource` (`/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/runtime/docoved-access-and-knowledge-source-binding-model.md:45-60`, `/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/runtime/docoved-access-and-knowledge-source-binding-model.md:72-89`, `/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/plans/protocols/PRT-038-docoved-shared-platform-adoption-control-plane-and-workflow-backed-knowledge-import.md:231-258`). Но в platform protocols это правило не доведено до общей формулы вида “shared object stores generic linkage; product binding meaning lives in product overlay”.
- Для governed-content lifecycle не до конца разведены shared revision identity и product activation identity. В Docoved activation и active snapshot явно продуктовые (`docoved-agent/.../docoved-memory-bank-publication-and-active-snapshot-model.md:45-67`, `:128-159`), в SellerAgent live rollout идет через release assignment поверх repo publish (`seller-agent/.../business-profile-publication-model.md:72-117`). Значит, shared `SourceRevision` не может молча стать unified activation object. Пока это подразумевается, но не закреплено жестко.
- `Membership` определен как principal-to-workspace role/capability binding, и это хорошо, но протоколы пока не проговаривают в явной отрицательной форме, что channel/customer/source-specific permissions не должны подменять или раздувать `Membership` (`.memory-bank/spec/project/three-layer-product-line-architecture.md:129-136`, `.memory-bank/spec/security/auth-and-access.md:49-60`). Без этого легко скатиться к ситуации, где product-local access overlays начнут оформлять как варианты shared membership model.

# Что убрать/не вводить

- Не вводить `KnowledgeSource` как еще одну shared canonical entity, пока не будет прямо решено, что это не product-local read model. Сейчас правильнее считать shared сущностью `ConnectedSource`, а `KnowledgeSource` оставить Docoved- или surface-level названием.
- Не вводить `ImportReport` как новый object root в shared vocabulary. По текущим текстам это лучше выглядит как обязательный structured outcome у `ImportRun`, а не как отдельная сущность с собственной жизнью.
- Не вводить generic “content”, “content item”, “content project” или другую широкую сущность, которая попытается покрыть и SellerAgent business-profile publication, и Docoved knowledge snapshot. Это сразу размоет product meaning, который документы как раз стараются защитить.
- Не вводить shared activation entity в первой волне. У Docoved activation завязана на active snapshot, у SellerAgent rollout завязан на release assignment; искусственное выравнивание здесь будет ложной обобщенностью.
- Не расширять `Membership` до канальных, source-level или product-object grants. Shared membership должен оставаться workspace-scoped access binding, а продуктовые overlays должны жить отдельно.

# Что минимально добавить в протокол

- В `PRT-039` и/или в `control-plane-configuration-and-observability-surfaces.md` одной короткой нормой зафиксировать: `KnowledgeSource` не новый shared object root, а surface/read-model label над shared `ConnectedSource` плюс product-local bindings там, где это нужно. Это снимет двусмысленность без добавления новых сущностей.
- В `PRT-038` или `PRT-039` добавить relation rule для execution vocabulary: `ExecutionSession` остается runtime/kernel lifecycle object, а `ExecutionRun` используется как shared operational/domain read model для surfaces, tracing и workflow inspection. Даже одна такая фраза уберет ненужную конкуренцию терминов.
- В `PRT-040` заменить перечисление shared objects так, чтобы `ImportReport` не выглядел отдельной сущностью, и явно сказать: у `ImportRun` есть обязательный structured report/outcome skeleton с counts, warnings, unsupported items и next-action state.
- В `PRT-039` и `PRT-040` добавить ownership-формулу для bindings: shared object vocabulary хранит только generic refs и generic lifecycle/status; product-local refs вроде `knowledge_source_ref`, `business_profile_ref`, release/activation pointers и review policy refs не становятся shared canon, даже если UI показывает их рядом с shared object.
- В `PRT-040` полезно одной строкой закрепить: shared `SourceRevision` описывает candidate/published shared revision envelope, но product-serving truth остается локальной, например Docoved active snapshot или SellerAgent release assignment. Это минимальное, но важное ограничение против будущего semantic drift.

# Premature abstractions

- Единая shared “governed content model” поверх SellerAgent и Docoved. Общий lifecycle substrate уже есть; общий продуктовый смысл здесь преждевременен.
- Универсальный shared object для activation/promotion. Пока у продуктов разные serving truths, такая абстракция будет не упрощением, а потерей точности.
- Отдельная shared сущность для каждого report/result (`ImportReport`, возможно потом `ActivationReport`, и т.д.) до того, как доказано, что у них есть собственный lifecycle и ownership, а не просто structured outcome внутри run/revision objects.
- Попытка превратить `KnowledgeSource` в платформенный канон раньше, чем будет доказан второй реальный consumer вне Docoved.
- Попытка моделировать product-local approvals, review semantics и product-specific rights внутри shared membership/source/channel vocabulary вместо того, чтобы оставить их продуктовым overlay.
