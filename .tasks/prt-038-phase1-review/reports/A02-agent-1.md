## Пробелы и риски

- Терминология shared entities пока не сведена в один канон по документам и коду. Верхний словарь говорит `ExecutionRun`, `ConnectedSource`, `SourceRevision`, `TraceArtifact` ([PRT-038](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-038-platform-product-line-convergence-and-shared-substrate-extraction.md):140), `PRT-040` добавляет `ImportReport` как canonical shared object ([PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md):60), control-plane spec оперирует `KnowledgeSource` и `ExecutionTrace` read models ([control-plane-configuration-and-observability-surfaces.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md):80), а runtime code все еще держит `ExecutionSession` как основной объект ([kernel.ts](/Users/deksden/Documents/_Projects/bot-platform/packages/core/src/runtime/kernel.ts):94). Без явной alias/mapping policy почти неизбежно появятся shadow entities и “почти одинаковые” read models.
- `ConnectedSource` пока недоопределен как shared identity и ownership boundary. Архитектурный spec говорит, что source binding может идти к workspace, product instances и channels “where applicable” ([three-layer-product-line-architecture.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/project/three-layer-product-line-architecture.md):88), control-plane read model ожидает `KnowledgeSource` с workspace scope и bound product instances ([control-plane-configuration-and-observability-surfaces.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md):141), а Docoved поверх этого использует `knowledge_source_ref` как product meaning и channel-bound binding ([docoved-shared-platform-adoption-control-plane-and-workflow-backed-knowledge-import.md](/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/plans/protocols/PRT-038-docoved-shared-platform-adoption-control-plane-and-workflow-backed-knowledge-import.md):226). Не хватает явного правила: `ConnectedSource` всегда workspace-owned shared object или он может быть product-owned с shared оболочкой.
- `SourceRevision` и activation boundary описаны слишком слабо на shared уровне. `PRT-040` говорит про shared `SourceRevision` и optional later `ActivationDecision` ([PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md):62), но Docoved уже реально требует candidate/imported/verified/active/superseded, idempotency key и activation lock ([docoved-memory-bank-publication-and-active-snapshot-model.md](/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/runtime/docoved-memory-bank-publication-and-active-snapshot-model.md):121, [docoved-memory-bank-publication-and-active-snapshot-model.md](/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/runtime/docoved-memory-bank-publication-and-active-snapshot-model.md):147). Если shared слой не зафиксирует хотя бы минимальную lifecycle skeleton, продукты начнут по-разному трактовать, где заканчивается `SourceRevision` и начинается `KnowledgeSnapshot` или `BusinessProfileRelease`.
- `PipelineBinding` выглядит полезной named relation, но пока не выглядит обязательным самостоятельным aggregate/root entity. Runtime spec прямо говорит, что `Channel` owns pipeline binding ([pipeline-registry-and-binding-contract.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/pipeline-registry-and-binding-contract.md):127), а код валидирует binding просто как часть channel update через `pipelineId + channelKind + pipelineArgs`, без отдельного lifecycle объекта ([pipeline-registry.ts](/Users/deksden/Documents/_Projects/bot-platform/packages/core/src/runtime/pipeline-registry.ts):39). Если сейчас материализовать `PipelineBinding` как отдельную сущность “потому что она в списке”, это создаст лишнюю абстракцию и дублирование ownership с `Channel`.
- Для `Principal` не хватает явной формулировки про non-human/service actors. Auth spec уже разводит human login sessions и automation/deploy tokens ([auth-and-access.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/security/auth-and-access.md):100), но shared vocabulary перечисляет только `User`, `Principal`, `Session`, `Membership` без короткого правила, должен ли automation actor быть отдельным `Principal` kind или отдельной сущностью. Это маленький, но важный пробел: без него runtime identity снова начнет размазываться между `User`, session token и channel/customer actor.

## Что убрать/не вводить

- Не вводить generic shared entity вроде `Content`, `KnowledgeObject`, `GovernedDocument` или другого “общего контейнера смысла”. Текущая архитектура правильно держится на shared lifecycle objects и product-local meaning; размывать это нельзя. См. [PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md):134, [docoved-platform-adoption-boundary.md](/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/project/docoved-platform-adoption-boundary.md):37, [selleragent-platform-adoption-boundary.md](/Users/deksden/Documents/_Projects/seller-agent/.memory-bank/spec/project/selleragent-platform-adoption-boundary.md):36.
- Не вводить второй shared object рядом с `ConnectedSource` под именем `KnowledgeSource`. Для Docoved это нормальный product-local read model/alias, но на уровне платформы второй почти-синоним только усилит дрейф словаря. Либо канонизируем `ConnectedSource`, либо переименовываем весь shared слой, но не держим оба как равноправные сущности.
- Не вводить `PipelineBinding` как обязательный standalone table/API root в первой волне. Пока его фактическая семантика выглядит как validated relation внутри `Channel`, а не как объект с собственным жизненным циклом.
- Не вводить `ImportReport` как еще один durable shared root, если у него нет самостоятельного ownership и lifecycle. По текущему материалу это скорее structured output/read model `ImportRun`, чем отдельная первичная сущность.
- Не вводить shared generalized activation object для всех продуктов до того, как базовые `ConnectedSource` / `SourceRevision` / `ImportRun` получат минимально согласованный skeleton. `ActivationDecision` и `SourceProcessingProfile` в `PRT-040` правильно отмечены как later optional, и их не стоит тянуть в first-wave canon. См. [PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md):69.

## Что минимально добавить в протокол

- Добавить короткий vocabulary mapping appendix: canonical shared object -> допустимые alias/read-model names -> статус alias. Минимально нужно разрулить `ConnectedSource` vs `KnowledgeSource`, `ExecutionRun` vs `ExecutionSession` / `ExecutionTrace`, и `ImportReport` как root entity vs read model.
- Для `ConnectedSource` явно зафиксировать ownership и cardinality rule: кому он принадлежит по умолчанию, может ли один source быть связан с несколькими `ProductInstance`, может ли `Channel` хранить прямую source binding, и является ли Docoved `knowledge_source_ref` canonical alias к shared identity или product-local projection поверх нее.
- Для `SourceRevision` зафиксировать минимум shared lifecycle, не таща в платформу всю Docoved semantics. Достаточно минимума: `candidate`, `processed` или `imported`, terminal failure, product-reviewed terminal success handoff. Отдельно нужно зафиксировать минимальный provenance/idempotency key, чтобы продукты не придумывали несовместимые revision identities.
- Для `Principal` добавить одно поле уровня протокола, а не новую сущность: `principal_kind` или эквивалент (`human`, `service`, `automation`). Этого достаточно, чтобы не смешивать `User` record, operator principal и automation actor.
- Для `PipelineBinding` добавить явное правило placement: first-wave meaning = named relation/sub-object of `Channel`; повышение до самостоятельной shared entity допустимо только если появится собственный lifecycle, multi-binding per channel или независимая audit/history semantics.

## Premature abstractions

- Самостоятельный shared aggregate `PipelineBinding` уже сейчас. Данных пока достаточно лишь для relation-level semantics внутри `Channel`, а не для отдельного доменного корня.
- Универсальный shared activation model для SellerAgent и Docoved. У них похожий governed lifecycle, но разный product meaning, и общая абстракция здесь слишком рано станет ложной.
- Единый shared `KnowledgeSource`/`BusinessProfileSource`/`ContentSource` super-object, который пытается одновременно покрыть Docoved knowledge source и Seller business profile publication. Это именно тот случай false generic content, от которого документы пока удачно защищаются.
- Отдельные mandatory shared objects `ActivationDecision`, `SourceProcessingProfile`, `ImportReport` до стабилизации базового словаря. Сейчас это скорее extension points, чем доказанные first-wave сущности.
- Универсальная “runtime identity” сущность сверх `Principal`/`Session`, если проблему можно закрыть явным `principal_kind` и mapping rule. Добавление нового root entity здесь будет дороже, чем уточнение уже существующего словаря.
