# Что уже хорошо

- По control plane уже есть хорошая базовая процессная рамка: один canonical write path на класс объекта, явное разделение UI/CLI/direct-admin chat и backend-owned validation/auditability. Это последовательно зафиксировано в `bot-platform/.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md:45`, `:69`, `:150`, `:160`, `:171` и не оставляет ощущения, что разные surfaces могут "по-своему" трактовать channel/pipeline writes.
- `PRT-039` достаточно четко фиксирует shared vocabulary и ownership для каналов: capability vocabulary, shared channel model, write ownership, local product IA, отказ от premature hosted centralization. Для create/update flows по channels/pipeline bindings это уже хороший каркас: `bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:88`, `:122`, `:124`, `:158`, `:200`, `:219`.
- `pipeline-registry-and-binding-contract` хорошо отделяет, что принадлежит `Channel`, что `PipelineDefinition`, а что execution engine. Для validate/create/update binding это уже почти implementation-ready contract: `bot-platform/.memory-bank/spec/runtime/pipeline-registry-and-binding-contract.md:119`, `:129`, `:136`, `:143`, `:217`, `:243`, `:252`.
- Для Docoved уже есть сильная контрольная модель source/channel binding: explicit resolution order, explicit failure, запрет public override bound source. Это хороший пример того, как shared substrate должен доходить до runtime semantics, а не только до object names: `docoved-agent/.memory-bank/spec/runtime/docoved-access-and-knowledge-source-binding-model.md:31`, `:48`, `:70`, `:83`, `:91`.
- Для review/activation gates у Docoved уже есть зрелый reference model: snapshot state machine, verified-only activation, activation lock, rollback через pointer switch, а не через неявный mutation-in-place. Это именно тот уровень explicit transitions, которого ждешь от governed lifecycle: `docoved-agent/.memory-bank/spec/runtime/docoved-memory-bank-publication-and-active-snapshot-model.md:123`, `:136`, `:139`, `:152`, `:157`, `:270`; `docoved-agent/.memory-bank/scenarios/SCN-179-git-backed-memory-bank-snapshot-import-and-activation.md:81`, `:85`, `:87`.
- В Docoved уже есть и кодовый якорь для lifecycle, а не только prose: отдельные status enums, review decision, completion kind, агрегатор статуса и отдельные endpoints `/review`, `/execute`, `/fail`. Это подтверждает, что проблема уже не в отсутствии идеи, а в недоформулированном shared contract: `docoved-agent/packages/db/src/docoved-ingest-store.ts:11`, `:26`, `:28`, `:30`; `docoved-agent/apps/api/src/docoved-workflow-routes.ts:638`, `:647`, `:754`, `:904`, `:953`, `:973`.

# Пробелы и риски

- Главный gap: `PRT-040` описывает import lifecycle как последовательность шагов, но не как минимальную shared state model. Есть `ImportRun`, `ProcessingArtifact`, review/report skeleton и общий flow, но нет canonical statuses, allowed transitions, actor actions и terminal semantics. В итоге второй продукт почти гарантированно изобретет свой `review_required/publishable/activation_failed/...` dialect: `bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:65`, `:66`, `:111`, `:159`.
- В `PRT-040` недоопределен handoff между shared substrate и product-local importer/activation logic. Фразы "create candidate product revision" и "approve and activate through governed product rules" слишком широкие: неясно, что именно shared layer обязан вернуть продукту, что продукт обязан вернуть назад в shared `ImportRun`, где живет `candidateRevisionRef`, и кто фиксирует `review_required` vs `ready_for_activation`: `bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:118`, `:120`.
- Failure/retry semantics на shared уровне почти отсутствуют. Для snapshot lifecycle они есть у Docoved, но для shared `ImportRun` не зафиксировано, retry это новый run, новый attempt внутри того же run, resume существующего run или product-local concern. Без этого нельзя консистентно реализовать CLI/UI/chat status/readback и automation: `bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:111`; contrast: `docoved-agent/.memory-bank/spec/runtime/docoved-memory-bank-publication-and-active-snapshot-model.md:152`, `:157`.
- Shared protocol пока схлопывает review и activation в один общий хвост, тогда как реальная governed модель их разделяет. Для Docoved уже видно, что `review_required -> publishable -> snapshot_importing -> snapshot_imported -> active` это не один transition. Если в shared protocol оставить только "approve and activate", он будет недостаточно точным для продуктов с explicit pre-activation verification и rollback: `bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:120`; contrast: `docoved-agent/packages/db/src/docoved-ingest-store.ts:11`, `:26`, `:28`; `docoved-agent/.memory-bank/spec/runtime/docoved-memory-bank-publication-and-active-snapshot-model.md:123`, `:136`, `:139`.
- Shared control-plane layer еще не фиксирует минимальный contract для product-data binding. `PRT-039` допускает "optional product-local association refs", но в реальном Docoved runtime уже критично, что channel/surface-bound source не может быть overridden публичным вызовом. Пока shared layer не определит, где заканчивается generic `Channel` и начинается explicit binding contract к product data, UI/write ownership и runtime interpretation останутся размыты: `bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:124`, `:158`; `docoved-agent/.memory-bank/plans/protocols/PRT-038-docoved-shared-platform-adoption-control-plane-and-workflow-backed-knowledge-import.md:236`, `:248`, `:256`; `docoved-agent/.memory-bank/spec/runtime/docoved-access-and-knowledge-source-binding-model.md:48`.
- Execution diagnostics contract обещает больше, чем сейчас закреплено в code-level kernel contract. Spec требует attempts/retries/failovers и normalized run/step/attempt traces, но code-level kernel пока знает только `ExecutionSessionStatus = completed | blocked`, `ExecutionTraceStatus = completed | blocked | failed`. Для A03 это риск, потому что control-plane read model уже говорит про retries/failovers, а минимальный platform state contract их пока не несет: `bot-platform/.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md:137`; `bot-platform/.memory-bank/spec/runtime/agent-execution-kernel.md:193`, `:195`, `:197`, `:198`, `:243`; `bot-platform/packages/core/src/runtime/kernel.ts:24`, `:34`, `:36`.
- В shared-looking API contracts до сих пор течет legacy seller semantics. Даже в Docoved package contract у `Channel` и `KnowledgeSource` остаются `businessProfileId/businessProfileSlug`, параллельно с `workspaceRef/productInstanceRef`. Это не просто ownership smell; это процессный риск, потому что один и тот же write contract несет две интерпретации tenancy/binding: `docoved-agent/packages/api-contract/src/operations.ts:1587`, `:1592`, `:1593`, `:1594`, `:1598`, `:1657`, `:1662`, `:1663`.

# Что убрать/не вводить

- Не вводить approval workflow для обычных channel/pipeline-binding writes. Для них уже достаточно synchronous validated mutation + audit trail; staged review/activation тут только размоет ownership и усложнит операторскую работу.
- Не превращать direct-admin chat в primary editor ни для channels/memberships, ни для import review/activation. И `PRT-039`, и operations spec правильно держат chat как bounded inspection/toggle surface: `bot-platform/.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md:69`; `seller-agent/.memory-bank/plans/protocols/PRT-008-selleragent-shared-platform-adoption-control-plane-and-business-profile-governance.md:114`.
- Не заталкивать SellerAgent business-profile release path в generic import model. У SellerAgent уже есть своя governed последовательность `validate -> verify repo -> publish -> create release -> assign release`, и протокол прямо говорит не заменять ее shared import flow: `seller-agent/.memory-bank/plans/protocols/PRT-008-selleragent-shared-platform-adoption-control-plane-and-business-profile-governance.md:234`, `:239`, `:241`, `:243`, `:245`.
- Не вводить в первой волне shared hosted control-plane service, editable pipeline registry CRUD, separate source-processing service или "generic no-code admin studio". Во всех базовых документах правильный курс уже другой: contracts/packages first, product-local implementation first: `bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:200`; `bot-platform/.memory-bank/spec/runtime/pipeline-registry-and-binding-contract.md:243`; `bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:145`.
- Не расширять дальше shared contracts legacy-полями вроде `businessProfileSlug` там, где target model уже `workspace + product instance + product-local binding`. Такие поля можно держать только как compatibility bridge, но не как growing canonical process contract.

# Что минимально добавить в протокол

- Добавить в `PRT-040` минимальный platform-level state vocabulary для `ImportRun`. Достаточно короткого набора, например: `accepted -> processing -> review_required | ready_for_activation -> activating -> completed`, плюс `failed` и `activation_failed`. Важно не число статусов, а то, чтобы у shared substrate появились canonical transition names, terminal states и actor-visible meanings.
- Явно зафиксировать набор shared actions над `ImportRun`: `start`, `refresh_status`, `record_failure`, `submit_for_review`, `approve_review`, `reject_review`, `request_activation`, `retry`, `rollback_activation` или сознательно указать, какие из них остаются product-local. Сейчас именно actions missing сильнее всего мешают implementation без домысливания.
- Добавить handoff contract между shared processor и product importer. Минимум нужен return envelope вида: `candidateRevisionRef?`, `nextState`, `blockingIssues[]`, `warnings[]`, `reportRef?`, `activationPreconditions?`. Без этого шаги 4-7 из lifecycle остаются narrative, а не executable contract.
- Явно разделить в shared protocol `review approval` и `activation`. Даже если activation policy product-local, shared layer должен уметь отразить, что revision уже review-approved, но еще не active. Иначе platform vocabulary не сможет честно описывать governed products вроде Docoved.
- Для bindings минимально зафиксировать, что `Channel` owns transport + entry pipeline, а binding к product data живет либо в отдельном shared binding object, либо в explicit product-local binding contract, но не в неявном "optional association ref". Для public surfaces нужно дописать правило уровня "bound source/policy refs are not overrideable from request payload" по аналогии с Docoved.
- Для retry semantics выбрать одно из двух и зафиксировать: либо retry создает новый attempt внутри того же `ImportRun`, либо retry создает successor run с явной ссылкой на parent. Любой вариант лучше текущей неопределенности.
- Для control-plane execution diagnostics минимально синхронизировать spec и kernel contract: либо сократить обещания про attempts/retries/failovers, либо поднять в shared runtime vocabulary хотя бы `attempt`/`retryCount`/`failureReason` как inspectable поля.

# Premature abstractions

- `ActivationDecision` пока выглядит преждевременно как shared first-class object. Пока нет второго реального продукта с тем же query/storage shape, достаточно shared transition names и product-local activation record.
- `SourceProcessingProfile` тоже рано поднимать в shared object model. Пока first wave говорит про один practical processor contract, профили лучше держать как configuration/metadata, а не как новый lifecycle object.
- Универсальный shared importer/activation engine вводить рано. Shared должен быть extraction bundle + handoff/report contract; interpretation, publication и activation policy должны оставаться product-local.
- Полностью editable pipeline registry тоже пока premature. Code-backed read-only catalog уже покрывает validation and selection; не видно причины превращать это в отдельный runtime-managed CRUD layer на первой волне.
- Shared durable `ExecutionSession` store тоже рано форсировать, пока даже repo-local kernel spec прямо говорит, что dedicated durable store deferred, а multiple workflow families with same resumability model еще не доказаны: `bot-platform/.memory-bank/spec/runtime/agent-execution-kernel.md:94`, `:95`.
