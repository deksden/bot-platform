# Что уже хорошо

- В платформенных specs уже есть правильный reliability baseline: один canonical write path на object class, backend-owned validation, bounded direct-admin chat и auditability как обязательное свойство, а не UI-опция. Это снижает риск drift между UI/CLI/chat и не поощряет “починим вручную через чат” ([control-plane spec](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md#L43), [control-plane spec](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md#L150), [PRT-039](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md#L158)).
- Базовый workflow contract уже требует explicit idempotency key, durable lifecycle, retry accounting и idempotent callbacks under duplicate delivery. Для A07 это сильная основа, потому что retry/replay semantics уже признаны first-class concerns ([workflow-framework-contract.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/workflow-framework-contract.md#L62), [workflow-framework-contract.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/workflow-framework-contract.md#L78), [workflow-framework-contract.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/workflow-framework-contract.md#L121)).
- Persistence boundary уже фиксирует правильные error classes (`Validation`, `Conflict`, `Unavailable`), explicit idempotency expectations и singleton-active rule для activation/cutover flows. То есть общий framework vocabulary для error handling уже есть, его не надо изобретать заново ([persistence-interface-and-store-boundary.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/persistence-interface-and-store-boundary.md#L71), [persistence-interface-and-store-boundary.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/persistence-interface-and-store-boundary.md#L82), [persistence-interface-and-store-boundary.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/persistence-interface-and-store-boundary.md#L89)).

Это правильный anti-pattern guard против “user-friendly simplification” ценой потери операционной правды ([observability-and-incident-diagnostics.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/observability-and-incident-diagnostics.md#L152), [observability-and-incident-diagnostics.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/observability-and-incident-diagnostics.md#L220), [observability-and-incident-diagnostics.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/observability-and-incident-diagnostics.md#L230)).

Это показывает, что нужная глубина semantics не теоретическая, а уже practically required ([docoved-memory-bank-publication-and-active-snapshot-model.md](/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/runtime/docoved-memory-bank-publication-and-active-snapshot-model.md#L121), [docoved-memory-bank-publication-and-active-snapshot-model.md](/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/runtime/docoved-memory-bank-publication-and-active-snapshot-model.md#L147)).

# Пробелы и риски

- В `PRT-040` lifecycle `ImportRun` описан почти целиком как happy-path sequence. Есть шаги “create/process/import/review/approve/activate”, но нет canonical transition map для `failed`, `retrying`, `superseded`, `canceled`, `duplicate`, `stuck waiting`, и нет разделения recoverable vs terminal failures. Для A07 это главный пробел: retry/recovery пока не отделены от normal path ([PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md#L111), [PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md#L159)).
- Activation boundary недоопределен именно как concurrency boundary. Shared persistence rule уже говорит “only one logical active state may be committed per scope”, но `PRT-040` не фиксирует, чем это достигается для `SourceRevision`: compare-and-swap, activation lock, unique active index, serial queue или другая гарантия. В результате риск double-activation и lost-update остается на уровне продукта по умолчанию ([persistence-interface-and-store-boundary.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/persistence-interface-and-store-boundary.md#L89), [PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md#L118), [docoved-memory-bank-publication-and-active-snapshot-model.md](/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/runtime/docoved-memory-bank-publication-and-active-snapshot-model.md#L152)).
- Bot submission и backend workflow склеены слишком слабо. Shared workflow contract требует idempotency key и duplicate-safe callbacks, но `PRT-040` не говорит, какой semantic operation dedupe’ится: повторная отправка того же файла из UI/chat, повторный callback workflow host, повторный approve/activate click. Это оставляет риск double-submit и duplicate import как раз в самом чувствительном месте ([workflow-framework-contract.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/workflow-framework-contract.md#L64), [workflow-framework-contract.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/workflow-framework-contract.md#L80), [PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md#L122)).
- `ImportRun` обязан выдавать report skeleton, но shared protocol не требует обязательной связки с `ExecutionRun`/attempt lineage/trace artifacts. Поэтому возможен плохой operational outcome: статус есть, но причины failure, exhaustion, retry history и correlation ids живут отдельно или теряются. Для incident review это уже reliability problem, а не просто observability gap ([PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md#L159), [control-plane spec](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md#L130), [workflow-framework-contract.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/workflow-framework-contract.md#L143)).
- `PRT-039` вводит memberships/channels/pipeline bindings как writable shared objects, но не фиксирует concurrency policy для самих mutations. Нет минимального требования на version precondition, compare-and-swap, conflict-on-stale-write или serialized owner path. Это открывает классические race cases: concurrent membership edits, stale channel reassignment, last-write-wins pipeline rebinding без явного conflict state ([PRT-039](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md#L72), [PRT-039](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md#L214), [persistence-interface-and-store-boundary.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/persistence-interface-and-store-boundary.md#L93)).
- В auth/access есть server-authoritative checks и session replacement rule, но нет shared failure semantics для membership/access changes, влияющих на long-running operations. Не проговорено, что делать с in-flight import/activation, если actor потерял membership посередине процесса, или если access overlay изменился между submit и approve. Это риск stale authorization decisions и непредсказуемых partial failures ([auth-and-access.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/security/auth-and-access.md#L57), [auth-and-access.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/security/auth-and-access.md#L84), [PRT-039](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md#L88)).
- В текущем runtime anchor уже виден опасный семантический сдвиг: `ExecutionTraceStatus` различает `completed | blocked | failed`, но `deriveExecutionSessionStatus` сводит любой `traceStatus !== completed` к `blocked`. То есть terminal failure в session layer легко теряет резкость и превращается в “blocked”. Для A07 это прямой сигнал, что error states пока недостаточно first-class даже в базовом коде ([kernel.ts](/Users/deksden/Documents/_Projects/bot-platform/packages/core/src/runtime/kernel.ts#L24), [kernel.ts](/Users/deksden/Documents/_Projects/bot-platform/packages/core/src/runtime/kernel.ts#L36), [execution-result.ts](/Users/deksden/Documents/_Projects/bot-platform/packages/core/src/runtime/execution-result.ts#L25)).
- `Channel` содержит `binding_status`, но shared protocol не задает разрешенные statuses и conflict/failure transitions для binding updates. При этом pipeline registry уже отделяет ownership и validation, а control-plane запрещает private validation. Значит, без явной error/state policy разные surfaces начнут по-разному трактовать broken binding, deprecated pipeline и failed reassignment ([PRT-039](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md#L124), [pipeline-registry-and-binding-contract.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/pipeline-registry-and-binding-contract.md#L119), [control-plane spec](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md#L152)).

# Что убрать/не вводить

- Не вводить silent downgrade из `failed` в `blocked`, `review_required` или “просто warning” ради user-friendly UX. Ошибка инфраструктуры или нарушение инварианта должна оставаться явно terminal/error state, а не растворяться в мягкой формулировке.
- Не вводить blanket retries для membership mutations, pipeline rebinding, approve/activate и других non-idempotent writes. Для этих операций retry допустим только при явном idempotency key или при attempt model; иначе это multiplier для duplicate side effects ([observability-and-incident-diagnostics.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/observability-and-incident-diagnostics.md#L230)).
- Не вводить chat-first remedial path для тяжелых recovery операций. Chat уже правильно ограничен inspection/status/narrow toggles; расширять его до свободных repair-команд означало бы обойти audit + validation именно там, где гонки и partial failures наиболее болезненны ([PRT-039](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md#L178), [PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md#L122)).
- Не вводить “автоматическое скрытое восстановление” через product-local fallback paths, если оно меняет lifecycle/result semantics. Для таких случаев observability spec уже требует explicit event и trace linkage; скрывать это нельзя ([observability-and-incident-diagnostics.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/observability-and-incident-diagnostics.md#L220)).
- Не вводить отдельный shared distributed lock manager как first reaction на все race risks. Сначала нужно зафиксировать какие именно invariants требуют serialization, а где достаточно uniqueness/CAS/idempotency. Иначе появится большая инфраструктурная абстракция до точного списка защищаемых операций.

# Что минимально добавить в протокол

- Для `ImportRun` добавить компактную shared state/error policy: минимальные states `accepted`, `processing`, `review_required`, `ready_for_activation`, `activating`, `completed`, `failed`, `superseded`, `canceled`; отдельно перечислить retryable transitions и terminal transitions.
- Для `SourceRevision`/activation добавить одно явное concurrency правило: “не более одного active per scope”, плюс допустимые способы реализации (`activation lock`, compare-and-swap с version check, unique-active constraint). Важно не навязывать storage implementation, а зафиксировать invariant и required conflict behavior.
- Зафиксировать semantic idempotency keys как минимум для трех операций: `ImportRun` start, workflow callback/update, activate verified revision. Без этого duplicate submit/delivery останутся “локальной реализационной деталью”, хотя это shared reliability concern.
- Для membership/channel/pipeline-binding writes добавить минимальный stale-write contract: mutation должна либо проходить с expected version/precondition, либо возвращать явный `Conflict`, а не last-write-wins по умолчанию.
- Обязать link refs между `ImportRun` и execution diagnostics: `execution_run_ref`, `trace_id` или equivalent attempt lineage, `requested_by_principal_ref`, `approved_by_principal_ref`, `activated_by_principal_ref`, `superseded_by_ref` где применимо.
- Явно отделить domain-facing blocked/review states от infrastructure/invariant failures в shared vocabulary. Сейчас документы это подразумевают, но кодовый anchor показывает, что без явной формулировки `failed` легко сплющивается в `blocked`.
- Для direct-admin chat зафиксировать mutation envelope: resolved principal, capability check, target object ref, idempotency/correlation key и audit fields до применения write. Это минимальная защита от спорных mixed bot/admin flows.

# Premature abstractions

- Универсальный shared “reliability engine” или generalized saga/orchestrator для всех imports, activations, memberships и channel changes сейчас преждевременен. Нужнее короткий invariant-first protocol, а не новая orchestration platform.
- Shared lock service/lock manager как обязательная часть первой волны тоже преждевременен. Большая часть описанных рисков закрывается проще: idempotency keys, explicit conflicts, single-active invariant и versioned writes.
- Общий cross-product failure taxonomy глубже уровня `Validation / Conflict / Unavailable / terminal failed / blocked-review` пока не нужен. Если сейчас пытаться канонизировать все error subtypes, получится ложная общность вместо надежного минимума.
- `ActivationDecision` как отдельный shared object и богатый `ImportReport` как самостоятельный durable root не нужны для закрытия текущих reliability gaps. Основная нехватка не в новых сущностях, а в том, что transition/error/idempotency semantics пока недоописаны в уже существующих `ImportRun` и `SourceRevision` ([PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md#L60)).
