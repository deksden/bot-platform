# Пробелы и риски

- Главный gap: `PRT-039` и `PRT-040` признают diagnostics surfaces, но почти не фиксируют protocol-level observability obligations для своих собственных critical paths. Shared ops-spec уже требует start/completion/failure events, correlation ids, structured log shape и traceable async states, однако child protocols пока не раскладывают эти требования на membership/channel/source/import flows ([observability-and-incident-diagnostics.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/observability-and-incident-diagnostics.md#L114), [observability-and-incident-diagnostics.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/observability-and-incident-diagnostics.md#L230), [observability-and-incident-diagnostics.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/observability-and-incident-diagnostics.md#L250), [PRT-039](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md#L212), [PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md#L169)).
- В `PRT-039` есть auditability “по наследству”, но нет explicit audit trail model для самых чувствительных мутаций первой волны: membership changes, channel rebinding, policy override assignment, knowledge-source attach/detach. Сейчас протокол говорит о shared objects и writable surfaces, но не говорит, какие mutation outcomes должны быть читаемы потом без DB-only spelunking: requested/applied/denied/conflicted/rolled_back, кто инициировал, по какому `operation_id`, с каким предыдущим binding/role/scope ([control-plane-configuration-and-observability-surfaces.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md#L160), [PRT-039](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md#L72), [PRT-039](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md#L171)).
- `PRT-039` также недоопределяет diagnostics для channel binding failures и access overlay changes. Channel detail read model из shared spec должен показывать effective pipeline args и operational status, но child protocol не требует failure reason, validation outcome, stale-write/conflict evidence, previous-to-current transition или explicit compatibility bridge diagnostics. Из-за этого UI/CLI/chat легко начнут давать разную “операционную правду” о том, почему binding сейчас broken или superseded ([control-plane-configuration-and-observability-surfaces.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md#L119), [control-plane-configuration-and-observability-surfaces.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md#L150), [PRT-039](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md#L124)).
- Для access/membership changes отсутствует явная observability story на случай, когда long-running work переживает изменение прав. Shared auth spec требует server-authoritative checks и auditable bypasses, но `PRT-039/040` не говорят, что должно остаться в trail, если submit сделал actor A, approve пытается actor B, а membership/role overlay успели измениться между этими шагами. Это уже operational investigation gap, а не просто security nuance ([auth-and-access.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/security/auth-and-access.md#L49), [auth-and-access.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/security/auth-and-access.md#L100), [PRT-039](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md#L106), [PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md#L111)).
- Самый заметный import-specific gap в `PRT-040`: `ImportRun` и `ImportReport` пока не обязаны нести canonical linkage к workflow/run-step-attempt diagnostics. В shared runtime уже есть vocabulary для run/step/attempt traces, workflow contract требует stable workflow run ids и callback correlation ids, но import protocol не требует `workflow_run_id`, `execution_trace_ref`, `processing_artifact_refs`, retry/failover lineage или attempt summary в read model/import report. Риск очевидный: статус import есть, а причины failure/retry/exhaustion живут отдельно и теряются при расследовании ([workflow-framework-contract.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/workflow-framework-contract.md#L62), [workflow-framework-contract.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/workflow-framework-contract.md#L143), [execution-traces-and-token-accounting.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/execution-traces-and-token-accounting.md#L44), [PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md#L111), [PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md#L159)).
- `PRT-040` описывает import lifecycle почти только как happy path и report skeleton, но не фиксирует обязательные observability checkpoints для background workflow: accepted/queued, processing started, extraction completed, importer handoff started/completed, review requested, activation started/completed/failed, superseded/canceled. Shared workflow и observability specs именно этого и требуют для async paths, поэтому отсутствие явной декомпозиции здесь оставляет critical path без договоренного event model ([observability-and-incident-diagnostics.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/observability-and-incident-diagnostics.md#L118), [observability-and-incident-diagnostics.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/observability-and-incident-diagnostics.md#L259), [workflow-framework-contract.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/workflow-framework-contract.md#L121), [PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md#L113)).
- `PRT-040` требует честную классификацию `supported/degraded/unsupported`, но не требует capture context, достаточный для forensic follow-up. Не хватает минимально обязательных investigation fields вроде source fingerprint/import input class, processor/importer version, actor/scope refs, source revision ref, submission channel/surface ref, artifact redaction/retention class, decisive reason codes по failure/degradation. Без этого report может быть честным, но все еще слишком бедным для повторяемого расследования ([PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md#L88), [PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md#L161), [decision-explanation-envelope.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/decision-explanation-envelope.md#L58)).
- Diagnostics viewers в `PRT-039` названы, но не привязаны к artifact governance. Shared trace-artifact spec требует elevated and auditable reads для raw prompt/context/heavy payloads и запрещает automatic dumps in operator/chat surfaces. Пока `PRT-039/040` этого явно не напоминают на control-plane/import surfaces, есть риск, что trace viewer/import diagnostics viewer будет реализован как raw bundle browser без правильной redaction/access discipline ([trace-artifact-governance.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/trace-artifact-governance.md#L102), [trace-artifact-governance.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/trace-artifact-governance.md#L113), [PRT-039](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md#L162)).
- Ни один из child protocols пока не говорит достаточно прямо: “использовать shared structured logs + canonical traces + governed artifacts, а не ad hoc product-local logger blobs”. При наличии уже сформулированной platform observability stack это важный omission, потому что именно import workflows и management mutations больше всего склонны обрастать локальными `console`-подобными trail’ами вместо общего evidence path ([observability-and-incident-diagnostics.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/observability-and-incident-diagnostics.md#L45), [trace-artifact-governance.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/trace-artifact-governance.md#L127)).

# Что убрать/не вводить

- Не вводить “шумный completeness theater” в виде blanket logging для каждого входного файла, каждого extracted fragment и каждого prompt/context payload. Shared governance уже говорит summary-first + selective heavy capture; импортный контур не должен превращаться в хранилище сырого forensic мусора ([trace-artifact-governance.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/trace-artifact-governance.md#L57), [trace-artifact-governance.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/trace-artifact-governance.md#L78)).
- Не вводить параллельный ad hoc audit trail рядом с canonical config mutation log и runtime trace. Два независимых источника “кто что изменил и почему сломалось” быстро дадут drift; нужен один shared evidence path с projection/read models сверху, а не отдельные журналы “для UI”, “для workflow”, “для импорта”.
- Не вводить raw heavy artifact dumps в direct-admin chat, operator UI previews или import status responses. Для этих поверхностей нужны bounded summaries и refs; raw payload access должен оставаться elevated and auditable ([control-plane-configuration-and-observability-surfaces.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md#L110), [trace-artifact-governance.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/trace-artifact-governance.md#L104)).
- Не вводить product-local event taxonomies, которые подменяют platform baseline. Если появятся отдельные названия событий и несовместимые статусы для membership changes, channel binding и import jobs, расследование cross-surface incidents снова станет ручным сопоставлением локальных диалектов.
- Не вводить “успокаивающие” success-like statuses для failures/degradations import flow. Для unsupported/degraded/failed веток нужно сохранить явную machine-readable правду, а не прятать ее в narrative report summary или в UI-friendly wording ([PRT-040](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md#L102), [observability-and-incident-diagnostics.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/observability-and-incident-diagnostics.md#L220)).

# Что минимально добавить в протокол

- В `PRT-039` добавить короткий mandatory observability packet для control-plane mutations: каждая mutation на membership/channel/pipeline binding/knowledge source должна иметь `request_id`, `correlation_id`, `operation_id`, actor ref, target ref, mutation outcome (`applied`, `denied`, `conflicted`, `failed`), old/new summary и timestamp. Это не новый subsystem, а просто protocol projection существующего auditability/logging baseline.
- В `PRT-039` явно перечислить обязательные diagnostics/readback expectations для channel binding и access changes: effective binding state, validation outcome, failure/conflict reason code, previous binding summary, last mutation ref, linked audit entry ref. Иначе “channel operational status” останется слишком расплывчатым ([control-plane-configuration-and-observability-surfaces.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md#L119)).
- В `PRT-039` добавить правило для diagnostics viewers: heavy artifacts и raw prompt/context payloads доступны только через governed artifact read path с elevated, auditable access; default surfaces показывают summary/ref/redaction status, а не сырой payload ([trace-artifact-governance.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/trace-artifact-governance.md#L102)).
- В `PRT-040` добавить обязательные linkage fields между `ImportRun` и execution/workflow observability: как минимум `workflow_run_id` или equivalent, `execution_trace_ref`, `processing_artifact_refs`, `requested_by_principal_ref`, `approved_by_principal_ref`, `activated_by_principal_ref`, `source_revision_ref`, `superseded_by_ref` when applicable.
- В `PRT-040` зафиксировать минимальный event/state packet для background import workflow: `import_run_created`, `import_processing_started`, `import_processing_completed`, `import_processing_failed`, `import_review_required`, `import_activation_started`, `import_activation_completed`, `import_activation_failed`, `import_run_superseded`, `import_run_canceled`. Можно назвать иначе, но protocol должен требовать именно эти checkpoints, а не только итоговый report.
- В `PRT-040` добавить mandatory investigation context в `ImportReport`/read model: source fingerprint, processor/importer version, input kind summary, degradation/unsupported reason codes, retry count, final failure class, artifact redaction state, retention class и concise operator summary. Это минимально доводит import diagnostics до incident-review usable состояния.
- В обоих child protocols отдельной строкой закрепить anti-ad-hoc rule: observability для shared flows строится через platform logger baseline, canonical execution traces и governed artifacts; product-local free-form logs допустимы только как дополнение, но не как единственный источник operational truth.
- В обоих child protocols стоит связать acceptance gates с observability evidence: critical routes/mutations возвращают correlation ids, background workflows имеют inspectable lifecycle state, а diagnostics surfaces позволяют расследовать failure без DB-only spelunking. Иначе observability останется “предполагаемым качеством”, но не protocol gate.

# Premature abstractions

- Отдельный shared “import observability platform” или второй diagnostics store для `ImportRun` сейчас преждевременен. Нужных primitives уже достаточно в platform logs, workflow ids, execution traces и governed artifacts; проблема в отсутствии explicit linkage, а не в нехватке еще одного слоя.
- Универсальный cross-product audit lake или generalized event bus ради membership/channel/import observability тоже преждевременен. Сначала нужно договорить минимальные canonical ids, outcome codes и read models в `PRT-039/040`; без этого новая инфраструктура только законсервирует неясность.
- Богатый universal “diagnostics viewer framework” для всех возможных raw artifacts тоже premature abstraction. Сейчас важнее узкое правило summary-first + governed raw access, чем построение большого UI shell для forensic browsing.
- Общий свободный “explanation blob” для import/result diagnostics не нужен. Платформа уже имеет bounded decision-explanation envelope, derived from canonical traces, и этого достаточно как общего explainability seam; добавлять еще один ad hoc narrative object было бы регрессом ([decision-explanation-envelope.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/decision-explanation-envelope.md#L45), [decision-explanation-envelope.md](/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/spec/runtime/decision-explanation-envelope.md#L127)).
