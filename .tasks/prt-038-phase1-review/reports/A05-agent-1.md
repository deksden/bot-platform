# Что уже хорошо

- `PRT-038` уже задает правильный first-wave default: не требуются ни единый shared hosted control-plane service, ни shared cross-product database; базовая ставка сделана на `shared contracts + product-local implementation` (`bot-platform/.memory-bank/plans/protocols/PRT-038-platform-product-line-convergence-and-shared-substrate-extraction.md:72`, `:76`). Для аспекта A05 это главный плюс.
- `ADR-005` и normative spec не просто называют middle layer, но и ограничивают его рост promotion rule'ом: capability поднимается в `bot-platform` только если она действительно product-agnostic или уже имеет несколько реальных потребителей (`bot-platform/.memory-bank/plans/adr/ADR-005-three-layer-product-line-architecture-and-shared-substrate-boundary.md:125`, `bot-platform/.memory-bank/spec/project/three-layer-product-line-architecture.md:175`, `bot-platform/.memory-bank/spec/project/feature-area-boundaries.md:137`). Это хороший антидот против overengineering "на вырост".
- По RBAC/control-plane линия тоже бережливая: `PRT-039` стандартизует capability families, но прямо запрещает замораживать один universal product RBAC ladder; role names и overlays остаются продуктовыми (`bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:88`, `:103`, `:106`). Это лучше, чем пытаться придумать "общую иерархию ролей" заранее.
- UI placement сформулирован в целом правильно: platform дает reusable management blocks / protected-shell primitives, а product repos собирают из них собственную IA; direct-admin chat ограничен inspection и узкими toggles, а не становится новым editor layer (`bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:158`, `:190`; `bot-platform/.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md:43`, `:69`, `:171`, `:183`).
- `PRT-040` хорошо удерживает source processing от premature service split: сначала контракт и package seam, first consumer использует его как in-process server-side module; отдельный service допускается только позже, если появится больше одного реального consumer или явная operational reason (`bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:149`, `:155`, `:157`; `bot-platform/.memory-bank/plans/adr/ADR-005-three-layer-product-line-architecture-and-shared-substrate-boundary.md:125`).
- Product-local normativity в `PRT-038` и repo-local packets SellerAgent/Docoved тоже работает на lean delivery: daily execution переносится в локальные протоколы, а не в giant cross-repo control document (`bot-platform/.memory-bank/plans/protocols/PRT-038-platform-product-line-convergence-and-shared-substrate-extraction.md:268`; `seller-agent/.memory-bank/plans/protocols/PRT-008-selleragent-shared-platform-adoption-control-plane-and-business-profile-governance.md:102`; `docoved-agent/.memory-bank/plans/protocols/PRT-038-docoved-shared-platform-adoption-control-plane-and-workflow-backed-knowledge-import.md:109`). Это снижает соблазн построить одну централизованную "мета-платформу" поверх всех продуктов.

# Пробелы и риски

- Самый заметный риск в `PRT-038` — формулировка `freezing the canonical shared object vocabulary` и список из 14 объектов как уже "fixed shared vocabulary" (`bot-platform/.memory-bank/plans/protocols/PRT-038-platform-product-line-convergence-and-shared-substrate-extraction.md:60`, `:140`). Для A05 это слишком сильная фиксация слишком рано: часть терминов действительно общая уже сейчас, но часть все еще живет с одним явным first consumer. В таком виде протокол может подтолкнуть команду к преждевременному universal object model вместо более дешевого contract-first подхода.
- В `PRT-039` сохраняется риск преждевременного framework UI layer. Формулировки про `reusable management and diagnostics surfaces`, `generic table/detail patterns for shared objects` и `materialize reusable protected-shell and diagnostics primitives` звучат полезно, но все еще могут быть прочитаны как разрешение строить platform-owned admin UI framework раньше, чем доказан второй потребитель (`bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:33`, `:38`, `:162`, `:167`, `:214`). Guardrail про local product IA есть, но его лучше ужесточить.
- `PRT-039` вводит capability families `policy.read` и `policy.manage`, хотя narrow shared policy object/model в пакете документов пока не зафиксирован (`bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:98`, `:99`). Это создает лишнюю гравитацию к универсальному policy subsystem или "общему движку политик", хотя phase 1 скорее требует конкретных policy refs для понятных объектов, а не отдельной абстрактной подсистемы.
- Channel substrate в `PRT-039` уже смотрит в сторону `bitrix24_bot` и "additional messenger adapters" (`bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:146`, `:152`). Само по себе это не ошибка, но для A05 есть риск, что команда начнет проектировать слишком богатую transport-agnostic channel meta-model "под все будущее" вместо минимального набора полей и capability flags, который нужен Telegram/email today.
- В `PRT-040` основной contract уже разумный, но optional-later objects `ActivationDecision` и `SourceProcessingProfile` создают ненужную архитектурную тягу (`bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:69`). На текущей волне это может быстро превратиться в registry/profiles/plugin architecture до того, как доказана повторная потребность.
- Output contract source processor в `PRT-040` хорошо описывает ожидаемый результат, но при неосторожной реализации может разрастись в generalized import platform: remote URLs, connected drives, отдельные processing profiles, per-format plugin seams и т.д. (`bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:77`, `:86`, `:90`). Протокол уже говорит "не сервис по умолчанию", но еще не говорит достаточно жестко "не строить platform of connectors/profiles/plugins в phase 1".
- В product-local packets lean stance mirrored хорошо, но это же показывает, что phase 1 на самом деле уже ориентирован на local execution packets. Поэтому любой новый shared abstraction, который потребует ежедневного cross-repo rereading или централизованного orchestration layer, будет идти против уже выбранного operating model (`seller-agent/.memory-bank/spec/project/selleragent-platform-adoption-boundary.md:84`, `:95`; `docoved-agent/.memory-bank/spec/project/docoved-platform-adoption-boundary.md:98`, `:109`).

# Что убрать/не вводить

- Не вводить в phase 1 отдельный shared hosted control-plane service, shared DB или "global admin backend". Текущие документы уже допускают package seams и local implementation; усиливать инфраструктурную централизацию сейчас не нужно (`bot-platform/.memory-bank/plans/protocols/PRT-038-platform-product-line-convergence-and-shared-substrate-extraction.md:72`; `bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:200`).
- Не вводить universal RBAC ladder, global role taxonomy или абстрактный policy engine "на будущее". Текущая лучшая практика здесь именно проще: shared capabilities, local role mapping (`bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:103`, `:118`; `bot-platform/.memory-bank/spec/security/auth-and-access.md:118`, `:136`).
- Не вводить platform-owned complete product UI, общий cross-product admin app или framework route tree. Для phase 1 достаточно narrow protected-shell primitives, selectors, forms, diagnostics blocks и shared contracts; product screens, IA и workflows должны оставаться в product repos (`bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:162`, `:169`, `:192`).
- Не вводить отдельный source-processing service/product, connector framework, profile registry или plugin architecture для ingest. Phase 1 нужен один practical contract и in-process module first (`bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:149`, `:155`; `docoved-agent/.memory-bank/plans/protocols/PRT-038-docoved-shared-platform-adoption-control-plane-and-workflow-backed-knowledge-import.md:287`, `:291`).
- Не тащить SellerAgent business-profile publication в "общий importer" только потому, что там тоже есть governed content. Это прямо против текущего boundary (`bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:55`, `:58`, `:144`; `seller-agent/.memory-bank/plans/protocols/PRT-008-selleragent-shared-platform-adoption-control-plane-and-business-profile-governance.md:136`, `:150`).
- Не проектировать богатый shared channel model под все будущие мессенджеры и transport quirks заранее. Для первой волны нужен минимальный common denominator, а не channel super-framework.

# Что минимально добавить в протокол

- В `PRT-038` стоит добавить явный anti-overengineering gate: "новый shared object / shared UI primitive / separate service допускается только если он уже product-agnostic на практике или имеет как минимум двух реальных потребителей". Сейчас этот принцип живет в spec/ADR, но его полезно поднять прямо в active execution protocol (`bot-platform/.memory-bank/spec/project/three-layer-product-line-architecture.md:177`, `bot-platform/.memory-bank/spec/project/feature-area-boundaries.md:139`).
- В `PRT-038` лучше разделить `canonical shared object vocabulary` на две корзины: `phase-1 mandatory shared terms` и `provisional candidate shared terms`. Это снимет давление строить полный универсальный object model там, где пока доказан только shared contract language.
- В `PRT-039` нужно прямо записать, что phase 1 разрешает только `contracts + headless/shared primitives + bounded read models`, но не `platform-owned complete admin application`. Текущая формулировка это подразумевает, но не запрещает достаточно явно.
- В `PRT-039` имеет смысл сузить или отложить `policy.read/policy.manage`: либо привязать их к конкретным policy-ref object classes, либо честно объявить, что universal shared policy subsystem не входит в phase 1.
- В `PRT-039` стоит добавить отрицательное правило по UI: platform не вводит mandatory framework route tree, global navigation schema и shared table/detail library beyond the narrow set needed by two actual products.
- В `PRT-040` нужно явно зафиксировать отрицательный список phase 1: no separate service, no connector marketplace, no profile registry, no per-format plugin framework, no remote-source platformization. Это уберет соблазн "подготовиться к будущему" ценой первой волны.
- В `PRT-040` полезно дописать extraction gate для source processing в стиле: "separate service possible only after second real consumer or concrete operations bottleneck". Сейчас это сказано по смыслу, но лучше сделать это отдельным protocol rule, а не только narrative remark (`bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:155`).

# Premature abstractions

- `ActivationDecision` как shared first-class object пока преждевременен. На текущей волне достаточно shared transition/report vocabulary и product-local activation semantics (`bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:69`).
- `SourceProcessingProfile` тоже выглядит premature abstraction. Пока нет второго потребителя с отличимой, но действительно общей profile semantics, это лучше держать как local config/metadata, а не как shared lifecycle object (`bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:71`).
- `policy.read` / `policy.manage` в текущем виде ближе к premature abstraction, чем к proven shared contract. Сначала нужен узкий concrete object boundary, потом уже общий policy layer.
- `generic table/detail patterns for shared objects` и разрастание `protected shell` в framework-owned UI layer тоже premature, пока phase 1 еще даже не доказал минимальный общий набор экранных примитивов на двух продуктах (`bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:162`, `:167`).
- Проектирование универсального channel substrate "под Telegram + email + Bitrix24 + дополнительные мессенджеры" сверх минимальных capability flags тоже будет premature abstraction, если начать закладывать transport-specific richness заранее (`bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:136`, `:146`).
- Отдельный source-processing service/product остается classic premature abstraction для этой волны; текущая лучшая практика здесь именно simpler package seam + local deployment (`bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:149`, `:155`; `bot-platform/.memory-bank/plans/adr/ADR-005-three-layer-product-line-architecture-and-shared-substrate-boundary.md:125`).
