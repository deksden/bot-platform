# Что уже хорошо

- В `PRT-039` уже хорошо зафиксирован каркас control-plane: есть канонический vocabulary для `Workspace`, `ProductInstance`, `Channel`, `PipelineBinding`, `ExecutionRun`, `TraceArtifact`, а также явное разделение capability vocabulary и product-local role overlays. Это снижает риск того, что разные продукты начнут по-разному трактовать один и тот же bind или access object (`.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:63-120`).
- Для write ownership есть полезная и достаточно строгая рамка: UI, CLI и direct-admin chat разведены по ролям, а direct chat прямо ограничен inspection/status/toggles и не объявлен полноценным editor surface (`.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:158-198`, `.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md:43-79`, `.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md:92-116`).
- Для pipeline binding уже есть хороший контрактный минимум: registry-backed validation, отделение `pipeline` от `product instance`, ограничение `pipelineArgs`, совместимость по `channelKind`, порядок default resolution через channel override -> pipeline defaults -> system defaults (`.memory-bank/spec/runtime/pipeline-registry-and-binding-contract.md:53-61`, `.memory-bank/spec/runtime/pipeline-registry-and-binding-contract.md:63-75`, `.memory-bank/spec/runtime/pipeline-registry-and-binding-contract.md:119-163`, `.memory-bank/spec/runtime/pipeline-registry-and-binding-contract.md:243-262`).
- В `control-plane-configuration-and-observability-surfaces.md` хорошо зафиксировано требование одного write path и одной validation contract на object class, плюс auditability для всех config mutations. Это сильная база для дальнейших stateful flows (`.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md:43-51`, `.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md:150-167`).
- В `PRT-040` уже есть правильный shared contract для source processing: входные классы, extraction bundle, honesty rule с `supported | degraded | unsupported`, запрет на silent drop. Это снимает большую часть двусмысленности на pre-import этапе (`.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:77-109`).
- Там же правильно задан базовый import shape: input -> `ImportRun` -> extraction bundle -> product importer -> candidate revision -> report/review -> approve/activate. Для first-wave shared substrate это удачная skeleton-модель (`.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:111-167`).
- Product-local Docoved документы показывают, что более строгая stateful модель в принципе нужна и реализуема: там уже есть explicit lifecycle, state machine, idempotency, activation locking и разделение ownership между ingest surface, workflow host, core и runtime (`/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/runtime/docoved-memory-bank-publication-and-active-snapshot-model.md:110-159`, `/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/architecture/domains/docoved-agentic-ingest-and-knowledge-projection-model.md:46-91`, `/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/architecture/domains/docoved-agentic-ingest-and-knowledge-projection-model.md:155-168`, `/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/architecture/domains/docoved-agentic-ingest-and-knowledge-projection-model.md:275-291`).

# Пробелы и риски

- Главный пробел: в shared protocol есть lifecycle shape, но нет explicit shared state model для `ImportRun`, `SourceRevision` и `PipelineBinding`. `PRT-040` перечисляет шаги процесса, но не задает допустимые состояния, переходы, terminal states и recovery paths. Из-за этого реализация `create`, `fail`, `retry`, `approve`, `activate`, `rollback` все еще требует домысливания (`.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:111-167`).
- `ImportReport` сейчас завершает flow слишком свободным полем "product-specific next action state such as `review_required`, `ready_for_activation`, or `failed`". Это полезно как idea, но недостаточно как contract: неясно, это shared enum, product extension point, terminal status или UI hint. В таком виде разные продукты почти наверняка начнут кодировать несовместимые universes статусов (`.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:159-167`).
- Не описан handoff contract между shared `ImportRun` и product-local candidate revision. В current text есть шаг "hand the bundle to the product-specific importer" и потом "create candidate product revision", но не определено, что именно importer обязан вернуть: candidate ref, review state, activation readiness, failure kind, partial success semantics, lineage refs. Это самый опасный under-specified handoff в A03 (`.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:113-120`).
- Не зафиксированы retry/idempotency semantics на shared import level. Для Docoved snapshot lifecycle они подробно описаны, но в shared protocol этого нет. Значит повторная загрузка того же input, re-delivery из bot/chat, повторный callback workflow host или repeated approve/activate пока не имеют общей contract truth (`/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/runtime/docoved-memory-bank-publication-and-active-snapshot-model.md:147-159`).
- Нет явного shared boundary между `ExecutionRun`/workflow state и control-plane state mutations. Control-plane docs требуют inspect execution run, attempts, retries and failovers, но не связывают это нормативно с mutation lifecycle channel binding/import activation. В итоге run observability и object lifecycle сейчас живут рядом, но не в одном process contract (`.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md:130-139`, `.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md:171-181`).
- `PRT-039` вводит `binding_status` у `Channel`, но не объясняет его state universe и allowed transitions. Непонятно, чем различаются draft/inactive/validated/broken/disabled states, кто их выставляет и как они связаны с runtime eligibility (`.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:124-156`).
- Write ownership между UI, CLI, bot chat и backend workflow обозначен на уровне surface roles, но не доведен до mutation authority per action. Например, кто имеет право только `start import`, кто может `retry`, кто может `approve`, кто может `activate`, а кто может лишь `read`/`request` эти действия, в shared protocol пока не разложено (`.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:158-188`, `.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md:92-116`).
- Source binding и channel binding описаны как соседние вещи, но их взаимосвязь в cross-product substrate не доведена до общего resolution contract. Для Docoved есть четкий `knowledge_source_ref` resolution order и запрет override bound source, а на платформенном уровне аналогичного правила для governed-content-backed channels еще нет (`/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/runtime/docoved-access-and-knowledge-source-binding-model.md:31-89`).
- Есть и признак документ/код drift по pipeline contracts. Документ описывает `PipelineDefinition` со `status`, `pipelineDefaults`, `allowedCapabilities`, optional compatibility notes, а текущий code anchor содержит только `pipelineId`, `workflowFamily`, `label`, `supportedChannelKinds`, arg keys, `defaultModelPolicyRef`, `allowedResultIntents` (`.memory-bank/spec/runtime/pipeline-registry-and-binding-contract.md:76-117` vs `packages/core/src/runtime/pipeline-registry.ts:1-15`). Для A03 это риск: protocol already speaks in richer contract terms than the current executable seam.
- Похожая проблема с execution lifecycle: в spec `ExecutionSession` описан как lifecycle carrier со state, attempts, traces, artifacts, intents и reasons, а текущий code contract сужает `ExecutionSessionStatus` до `completed | blocked`, а `ExecutionTraceStatus` до `completed | blocked | failed`. Для kernel этого может быть достаточно сегодня, но как общий anchor для import/review/activation flows это слишком бедный state vocabulary (`.memory-bank/spec/runtime/agent-execution-kernel.md:84-97` vs `packages/core/src/runtime/kernel.ts:24-36`, `packages/core/src/runtime/kernel.ts:94-129`).

# Что убрать/не вводить

- Не вводить generic no-code admin studio или editable pipeline-definition CRUD в first wave. И control-plane spec, и pipeline registry spec правильно ориентируют на code-backed registry и contract-driven writes; это нужно сохранить (`.memory-bank/spec/operations/control-plane-configuration-and-observability-surfaces.md:171-183`, `.memory-bank/spec/runtime/pipeline-registry-and-binding-contract.md:243-250`).
- Не превращать direct-admin chat в surface для complex config editing, review bypass или activation bypass. Это прямо противоречит и `PRT-039`, и `PRT-040`, и это самый короткий путь к разъезжающимся process contracts (`.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:178-188`, `.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:122-132`).
- Не вводить shared cross-product database/service только ради того, чтобы "сделать state machine общей". Проблема сейчас не в deployment topology, а в недостаточно явных contracts. `PRT-039` и `PRT-040` верно держат storage/service product-local for now (`.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:200-210`, `.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:149-157`).
- Не затаскивать SellerAgent business-profile publication в generic import substrate. Протокол уже предупреждает об этом, и в A03 это особенно важно: иначе shared state model начнет кодировать Seller-specific release semantics (`.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:144-147`).
- Не вводить pseudo-universal product RBAC ladder. Для process contracts нужен action-level authority, а не одна общая ролевая taxonomy (`.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:88-120`, `.memory-bank/spec/security/auth-and-access.md:118-126`).

# Что минимально добавить в протокол

- Для `ImportRun` нужен минимальный shared state machine. Достаточно маленького набора вроде: `received -> processing -> processed -> importer_running -> review_required | ready_for_activation | failed`, плюс разрешенные retry transitions из `failed` и explicit terminal semantics.
- Для review/activation нужен action contract, а не только narrative step list. Минимум: `approve`, `reject/fail`, `activate`, `retry`, `rollback` с actor requirements, preconditions, idempotency expectations и result envelope.
- Для handoff между shared importer substrate и product-local importer нужен explicit return contract. Минимум: `candidateRef`, `candidateKind`, `reviewState`, `activationEligibility`, `blockingIssues[]`, `artifactRefs[]`, `lineageRefs`.
- Для `ImportReport` нужно разделить shared и product-local state. Shared enum должен быть маленьким и process-oriented, а product-specific semantics могут жить в отдельном extension field. Иначе `next action state` станет общей помойкой.
- Для `PipelineBinding` нужен explicit lifecycle contract поверх текущего validation contract. Хотя бы `draft | active | disabled | error` с описанием, когда binding eligible for execution и кто переводит его между этими состояниями.
- Для retry semantics нужен shared idempotency key rule. На уровне протокола достаточно зафиксировать, что повторный submit того же semantic import request converges to one logical `ImportRun` or one superseding relation, а repeated `activate` для того же approved candidate не создает duplicate effect.
- Для failure semantics нужен маленький taxonomy split: `validation_failure`, `processing_failure`, `importer_failure`, `review_rejected`, `activation_failure`. Это уже сильно уменьшит cross-surface ambiguity.
- Для source/channel ownership нужен общий resolution rule в духе Docoved: bound channel/surface owns the governed source unless an explicitly authorized caller-selected override mode is declared. Это важно для channels + pipeline bindings + governed content в одной модели (`/Users/deksden/Documents/_Projects/docoved-agent/.memory-bank/spec/runtime/docoved-access-and-knowledge-source-binding-model.md:36-89`).
- Для observability стоит добавить обязательные lineage refs между `ImportRun`, workflow/execution run, candidate revision и activation event. Иначе diagnostics будут inspectable по отдельности, но не как единый process chain.

# Premature abstractions

- `ActivationDecision` как общий полноценный объект пока выглядит преждевременным. В `PRT-040` он уже помечен как optional later shared object, и это правильный статус: сначала нужен ясный action/state contract, а не отдельная сущность (`.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:69-71`).
- Shared durable kernel-session store для всех workflow families тоже преждевременен. Собственная kernel spec прямо говорит, что такой store отложен до момента, когда multiple workflow families реально разделят одну resumable persistence model (`.memory-bank/spec/runtime/agent-execution-kernel.md:94-97`).
- Универсальный workflow builder/pipeline graph abstraction не нужен. Pipeline registry уже правильно ограничен реальными pipeline families, а не произвольной композиционной системой (`.memory-bank/spec/runtime/pipeline-registry-and-binding-contract.md:264-269`, `.memory-bank/spec/runtime/pipeline-registry-and-binding-contract.md:271-278`).
- Отдельный source-processing product/service на этой стадии тоже premature. Сначала нужен package seam и общий contract; extraction into service имеет смысл только после появления второго реального consumer и явной operational причины (`.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:149-157`).
- Универсальная cross-product review policy тоже premature. Shared layer должен фиксировать transitions и authority envelope, а не унифицировать Docoved review semantics с Seller review/takeover semantics.
