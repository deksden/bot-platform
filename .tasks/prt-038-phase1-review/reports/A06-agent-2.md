# Пробелы и риски

- Самый важный A06-риск: протоколы хорошо называют duplicated runtime tails, но пока недостаточно жестко различают reusable mechanism и reusable catalog. В коде уже есть generic registry helper в `bot-platform`, но concrete catalog с `seller_conversation`, `draft_review`, `docoved_answer` живет как duplicated product file в обоих репозиториях (`/Users/deksden/Documents/_Projects/bot-platform/packages/core/src/runtime/pipeline-registry.ts:39-167` против `/Users/deksden/Documents/_Projects/seller-agent/packages/core/src/runtime/pipelines.ts:3-130` и `/Users/deksden/Documents/_Projects/docoved-agent/packages/core/src/runtime/pipelines.ts:3-130`). Если в этой волне "переиспользование" поймут как перенос всего каталога в platform, это будет не cleanup, а преждевременная централизация product pipeline semantics.
- `PRT-038` фиксирует широкую canonical shared vocabulary как уже `fixed` (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-038-platform-product-line-convergence-and-shared-substrate-extraction.md:140-158`). Для A06 это риск, потому что такая формулировка сокращает пространство для refactoring by evidence: часть объектов действительно shared, но часть пока еще выглядит как first-consumer-biased contract surface, а не как доказанный multi-product core.
- В SellerAgent остается скрытая product integration, маскирующаяся под локальную runtime truth: conversation service импортирует `createDocovedExecutionService`, `DocovedReplyContextMessage`, `DocovedTurnRelation`, а также `./docoved-entry` helpers прямо внутри SellerAgent canonical conversation service (`/Users/deksden/Documents/_Projects/seller-agent/packages/core/src/conversations/service.ts:75-92`). Это не повод тащить Docoved logic в shared слой; наоборот, это smell, который лучше явно оформить как bounded integration seam.
- Протокол называет cleanup tail'ы, но не превращает их в обязательный refactoring checklist. Между тем fake shared bucket и legacy ownership drift подтверждаются кодом: SellerAgent apps все еще зависят от `../../packages/shared` (`/Users/deksden/Documents/_Projects/seller-agent/apps/cli/tsconfig.json:9-25`, `/Users/deksden/Documents/_Projects/seller-agent/apps/server/tsconfig.json:9-25`), а SellerAgent ownership doc прямо говорит, что `packages/shared` - migration bucket, not a meaningful owner (`/Users/deksden/Documents/_Projects/seller-agent/.memory-bank/spec/project/business-profile-project-and-package-ownership.md:24-33`, `:143-174`).
- Residual `sales-agent` assumptions остаются не только в архиве, но и в живых surfaces: `serviceName = 'sales-agent-platform'` в SellerAgent server bootstrap (`/Users/deksden/Documents/_Projects/seller-agent/apps/server/src/server-composition/bootstrap-support.ts:126-150`), а у Docoved package metadata до сих пор repository/homepage указывают на `sales-agent.git` (`/Users/deksden/Documents/_Projects/docoved-agent/packages/api-contract/package.json:20-24`). Это не "косметика": такие хвосты продолжают закреплять ложного owner'а в publish/runtime artifacts.
- Есть и скрытые server-only integration paths, которые протокол упоминает скорее по смыслу, чем как конкретный smell class. В том же SellerAgent bootstrap `OPENAI_API_KEY` fallback идет через `DOCOVED_BETA_OPENAI_API_KEY` и `DOCOVED_PROD_OPENAI_API_KEY` (`/Users/deksden/Documents/_Projects/seller-agent/apps/server/src/server-composition/bootstrap-support.ts:145-150`). Это уже cross-product operational coupling, которую нельзя выдавать за reusable shared logic.

# Что убрать/не вводить

- Не вводить platform-owned единый concrete pipeline catalog для всех продуктов. Переиспользуемым seam здесь уже является validator/registry helper, а не объединенный список product pipeline ids.
- Не консервировать hidden product integrations внутри shared/runtime owners. То, что SellerAgent использует Docoved-facing execution helpers, должно остаться явно product-integration seam, а не аргументом "это уже shared".
- Не оставлять `packages/shared` как долговечный контейнер для mixed ownership. Для A06 это прямо anti-pattern, потому что он скрывает, что именно надо либо поднять в `bot-platform`, либо вернуть в product owner.
- Не тащить в phase 1 новые compat wrappers и branding tails вокруг `sales-agent`. Архивный lineage нужен для понимания истории, но не должен продолжать жить в service names, package metadata и publish-facing identity.
- Не строить generic governed-content/import abstraction так, чтобы туда затянуть SellerAgent business-profile publication. `PRT-040` правильно это отрицает; важно не размыть это во время реализации (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:55-58`, `:144-147`).
- Не вводить shared admin/UI framework "на вырост" поверх формулировок про reusable shells и table/detail patterns. Reuse нужен на уровне bounded primitives, а не как новая platform-owned app layer (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:160-199`).

# Что минимально добавить в протокол

- Явное правило: если найден identical runtime helper/catalog в двух продуктах, следующая волна должна сначала классифицировать его как `shared mechanism` или `product catalog`, и только потом переносить. Сейчас этот шаг подразумевается, но не зафиксирован.
- Отдельный cleanup backlog для `W5` с тремя обязательными классами хвостов: `packages/shared` consumers, residual `sales-agent` metadata/branding, hidden cross-product server config fallbacks. Сейчас `PRT-038` их называет, но не задает как проверяемые deliverables (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-038-platform-product-line-convergence-and-shared-substrate-extraction.md:206-212`).
- Правило "reuse existing seam first": если в `bot-platform` уже есть generic helper, новые refactor waves не должны создавать еще один parallel abstraction в product repo. Кейс `pipeline-registry.ts` показывает, что это правило нужно проговорить явно.
- Короткий anti-smell appendix по hidden integrations: product-specific execution helpers, env/config fallbacks и compat imports не считаются shared substrate evidence сами по себе; они должны либо стать explicit product adapter, либо быть удалены.
- Для `PRT-039` полезно дописать, что shared scope включает `channel/pipeline binding contracts`, но не автоматически включает platform ownership над полным pipeline catalog. Это снимет риск неправильного "reuse through centralization".
- Для `PRT-040` полезно добавить явный cleanup gate: reuse governed-content pieces only where semantics match, but also retire product-local pseudo-generic wrappers when real ownership is known. Иначе shared import wave пройдет поверх старых ambiguities, не устранив их.

# Premature abstractions

- Platform-owned concrete pipeline catalog с `seller_conversation`, `draft_review`, `docoved_answer` был бы premature abstraction. Shared здесь уже доказан на уровне registry mechanics, а не на уровне полного списка pipeline families.
- `policy.read` / `policy.manage` в `PRT-039` пока слишком широки и могут стать контейнером для всего подряд. Для A06 это плохая абстракция, потому что она создает новый "shared bucket" вместо явного owner-specific split (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:88-104`).

В phase 1 shared должен держать минимальный report contract, а не навязывать полноценную универсальную report domain, пока first consumer все еще Docoved-heavy (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-040-governed-content-source-processing-and-workflow-backed-import-substrate.md:60-67`, `:159-167`).

- Reusable protected shell + generic table/detail patterns легко превратить в новую platform UI meta-layer. Для A06 это classic premature abstraction: сначала нужны 2-3 доказанных bounded primitives на двух продуктах, потом framework language, а не наоборот (`/Users/deksden/Documents/_Projects/bot-platform/.memory-bank/plans/protocols/PRT-039-shared-control-plane-access-channel-and-management-substrate.md:160-199`).
